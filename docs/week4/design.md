# 4주차 설계: 상품 조회에서 인덱스·좋아요 카운터·Redis를 선택한 이유

상품 목록 조회에서 인덱스로 탐색·정렬 비용을 줄이고, 별도 카운터로 좋아요 집계를 줄인 뒤, Redis로 같은 목록의 계산 결과를 재사용했다.

## 1. 상황: SQL이 적어도 읽는 데이터는 많았다

기존 목록 조회는 상품과 브랜드를 읽으면서 `product_likes`에서 상품별 좋아요 수를 COUNT했다. 목록·전체 개수 조회로 SQL은 두 번 실행했지만, 목록 SQL 안에서 좋아요 관계를 반복 탐색했다.

상품 100만 개·좋아요 200만 개로 인덱스 전후를 비교했다. 이후 인기 상품의 집계 비용을 확인하려고 좋아요를 500만 개로 늘려 카운터 방식과 비교했다. 두 실험의 데이터 조건과 측정 단위는 구분한다.

## 2. 인덱스: 어떤 탐색을 줄이려고 했나

### 데이터 분포와 조회 조건

| 항목 | 실험 데이터 | 인덱스를 정할 때 고려한 점 |
| --- | --- | --- |
| 브랜드 | 2개에 상품 50만 개씩. 상품 ID 순서에서 5개 단위로 브랜드를 번갈아 배치 | 브랜드 하나를 골라도 50만 개가 남아 가격순 탐색까지 필요하다. |
| 가격 | 1,000·5,000·10,000·30,000·50,000·100,000원을 거의 같은 수로 배정 | 브랜드 안에서 같은 가격이 약 8.3만 개씩 생겨 동점 정렬이 필요하다. |
| 삭제 여부 | 상품·브랜드 모두 미삭제 | 삭제 조건으로 줄어드는 상품은 없다. |
| 좋아요 | 상품별 0~4개를 고르게 배정, 총 200만 개 | 상품당 평균 2개를 세기 위해 전체 관계를 탐색하는 비용을 줄여야 한다. |

브랜드를 섞어 특정 브랜드가 상품 ID 한 구간에 몰리지 않게 했다. 완전한 무작위 대신 같은 조건을 재현할 수 있는 규칙적 분포를 사용했다.

측정한 요청은 한 브랜드의 가격순 첫 페이지 20개다. 상품과 브랜드가 모두 미삭제인 경우만 노출한다.

```sql
WHERE p.brand_id = :brandId
  AND p.deleted_at IS NULL AND b.deleted_at IS NULL
ORDER BY p.price ASC, p.id DESC
LIMIT 20 OFFSET 0
```

### 현재 인덱스의 열 순서와 정렬 방향

현재 코드의 상품 인덱스는 `(brand_id, price ASC, id DESC)`다.

| 구성 | 선택 근거 |
| --- | --- |
| `brand_id` | 지정한 브랜드의 범위를 먼저 찾는다. |
| `price ASC` | 해당 브랜드 안에서 낮은 가격순으로 읽는다. |
| `id DESC` | 같은 가격이면 상품 ID가 큰 순서로 읽어 동점 상품의 순서를 확정한다. |

브랜드가 두 개라 필터만으로는 절반밖에 줄이지 못한다. 브랜드 범위 안에서 가격·ID 순서로 읽고 첫 20개를 찾는 데 목적이 있다. 정렬 방향은 데이터가 많은 쪽이 아니라 API의 반환 순서에 맞췄다.

`price`와 `id`를 모두 ASC로 두면 정방향은 `가격 ASC·ID ASC`, 역방향은 `가격 DESC·ID DESC`다. 필요한 `가격 ASC·ID DESC`를 맞추기 위해 혼합 방향을 명시했다. [MySQL 정렬 최적화 문서](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html)를 참고했다.

기존 인덱스에는 `deleted_at`도 포함했다. 모두 미삭제인 실험에서는 필터로 줄어드는 상품이 없고, 이 열을 추가한 이득을 따로 측정하지 않아 제외했다. SQL의 삭제 제외 조건은 유지한다. 다만 COUNT에서 삭제 여부를 상품 행 대신 인덱스로 확인하던 이점은 잃을 수 있다. 삭제 비율이나 COUNT 비용이 커지면 다시 비교한다.

이 인덱스의 대상은 브랜드를 지정한 가격순 조회다. 전체 가격순·최신순·좋아요순의 정렬 비용까지 해결하지는 않는다.

### 좋아요 인덱스

기존 `(user_id, product_id)` 인덱스는 사용자별 관계를 모은다. 상품별 COUNT는 사용자 조건 없이 상품 ID만 지정했고, 실행계획에서는 관계 200만 개를 순회했다.

`(product_id)`를 추가해 해당 상품의 관계를 바로 찾도록 했다. 이 데이터에서는 상품당 평균 2개만 찾아 세면 된다. [MySQL 복합 인덱스 문서](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)를 참고했다.

### 비교 방법과 결과

MySQL 8.0.46, 컨테이너 메모리 2GiB·CPU 4코어, InnoDB 버퍼 풀 512MiB에서 Redis 없이 측정했다. PK·유니크 인덱스는 유지하고 조회용 인덱스만 바꿨다. 각 상태에서 5회 준비 실행 후 30회 순차 요청했다.

| 조회 인덱스 상태 | HTTP 중앙값(p50, ms) | HTTP p95(ms) | 요청당 SQL 수 |
| --- | ---: | ---: | ---: |
| 조회 인덱스 없음 | 2445.01 | 2472.74 | 2 |
| 상품 인덱스만 | 2241.80 | 2268.17 | 2 |
| 상품·좋아요 인덱스 | 47.63 | 50.04 | 2 |

세 상태의 상품·가격·좋아요 수·페이지 정보는 같았다. 상품 인덱스만으로는 좋아요 반복 탐색이 남아 개선이 작았다. 좋아요 인덱스를 추가한 뒤 응답 시간이 크게 줄었다.

| 실행계획에서 확인한 작업 | 조회 인덱스 없음 | 상품·좋아요 인덱스 |
| --- | --- | --- |
| 상품 탐색·정렬 | `ALL`: 예상 991,950행 → 실제 1,000,000행 × 1회. 필터 통과 50만 행 정렬 | `ref`: 예상 496,913행 → 실제 20행 × 1회. 별도 정렬 없음 |
| 상품별 좋아요 집계 | `index`: 예상 1,992,376행 → 실제 2,000,000행 × 20회 | `ref`: 예상 2행 → 실제 2행 × 20회 |
| 전체 개수 계산 | `ALL`: 예상 991,950행 → 실제 1,000,000행 × 1회 | `ref`: 예상 496,913행 → 실제 500,000행 × 1회. 커버링 인덱스 사용 |

예상 행수는 EXPLAIN의 `rows`, 실제 행수·반복은 EXPLAIN ANALYZE의 탐색 노드 `rows × loops`다. 목록 상품의 예상 약 50만 행과 실제 20행 차이는 `LIMIT 20`으로 탐색을 일찍 마친 결과다. 상품 조회는 `idx_products_brand_deleted_price_id`, 좋아요 조회는 `idx_product_likes_product_id`를 사용했다. 개선 전 좋아요 조회는 기존 `(user_id, product_id)` 유니크 인덱스 전체를 순회했다.

EXPLAIN ANALYZE와 함께 같은 연결에서 SELECT 전후의 `Handler_read_*` 차이도 확인했다. 목록의 `Handler_read_next`는 약 4,000만에서 59로, `Handler_read_rnd_next`는 1,000,001에서 0으로 줄었다. 상품 전체 탐색과 좋아요 관계 순회가 줄었다는 근거다. Handler 값은 디스크 I/O나 SQL 호출 횟수를 뜻하지 않는다.

전체 개수 계산은 여전히 50만 행을 읽었다. 측정은 로컬 순차 요청이며 동시 부하 성능은 포함하지 않는다.

## 3. 좋아요 집계: 인덱스만으로 충분했나

인덱스가 있어도 좋아요가 많은 상품은 관계를 많이 세어야 한다. 기존 200만 관계에 인기 상품 20개당 15만 개씩 추가해 총 500만 개로 늘렸다.

| 대안 | 장점 | 감수할 비용·문제 |
| --- | --- | --- |
| `product_likes`를 매번 COUNT | 원본 관계에서 계산하므로 별도 집계 값을 관리하지 않음 | 인기 상품의 많은 관계를 매번 읽음 |
| 페이지 선택 후 JOIN/GROUP BY | 가격순·최신순에서 해당 페이지의 상품만 집계 | 관계가 많으면 JOIN 중간 결과가 커짐. 전체 좋아요순은 집계·정렬 전에 페이지를 고를 수 없음 |
| `products.like_count`에 저장 | COUNT 없이 개수를 읽음 | 좋아요와 가격·재고 변경이 같은 상품 행에서 잠금 경합 |
| **별도 `product_like_counts`에 저장** | **COUNT 없이 개수를 읽고 상품 정보와 다른 행을 갱신** | **JOIN과 추가 쓰기, 초기 집계·일치 여부 관리 필요** |
| Redis 카운터·Sorted Set | 메모리에서 개수·순위 조회 | DB와의 불일치·재구축·Redis 장애 시 대체 조회 관리 필요 |
| 이벤트·배치로 지연 집계 | 변경을 모아 카운터 갱신 횟수를 줄임 | 개수 지연과 이벤트 중복·누락·재처리 관리 필요 |

COUNT와 JOIN/GROUP BY는 SQL로 비교했다. 좋아요가 몰린 조건에서는 JOIN/GROUP BY도 중간 결과가 커져 더 느려질 수 있었다. 상품 컬럼·Redis Sorted Set·지연 집계는 설계 대안으로 검토했다.

## 4. 선택: 좋아요 개수를 별도 테이블에 저장했다

반복 COUNT를 줄이면서 좋아요와 상품 정보의 쓰기가 같은 행에서 경합하지 않도록 별도 카운터를 선택했다.

| 테이블 | 저장하는 내용 |
| --- | --- |
| `products` | 상품 이름·가격·재고 |
| `product_likes` | 누가 어떤 상품에 좋아요를 눌렀는지 |
| `product_like_counts` | 상품별 좋아요 개수 |

원본 관계에서 계산할 수 있는 개수를 중복 저장하므로 비정규화다. 원본은 `product_likes`이며 카운터를 다시 만들거나 기존 데이터를 이행할 때 이 관계를 집계한다.

등록·취소 시 관계와 카운터를 같은 DB 트랜잭션에서 변경한다. 중복 등록은 늘리지 않고 실제 관계가 삭제될 때만 줄이며, 실패하면 함께 롤백한다.

가격순·최신순은 페이지를 고른 뒤 해당 상품의 카운터만 읽는다. 좋아요순은 DB에서 전체 후보의 카운터를 결합·정렬한 뒤 페이지를 고른다.

카운터에는 상품 ID 기본키를 두고 상품 테이블로 향하는 외래키나 JPA 연관관계는 추가하지 않았다. 카운터가 잠긴 동안 상품 가격 수정이 가능한지도 테스트했다. 같은 인기 상품의 카운터를 동시에 갱신하는 경합은 남는다.

## 5. Redis 도입 전: 무엇이 줄었고 무엇이 남았나

상품 100만 개·좋아요 500만 개에서 두 집계 방식을 비교했다. 두 방식 모두 삭제 열을 포함한 변경 전 상품 인덱스를 사용했고 Redis는 사용하지 않았다. 각 SQL을 2회 준비 실행한 뒤 번갈아 7회씩 측정했다. 아래 값은 목록 SQL 실행과 결과 수신 시간의 중앙값이며 HTTP 응답 시간이 아니다.

| 조회 상황 | `product_likes`에서 COUNT(ms) | `product_like_counts.like_count` 값 조회(ms) | 결과 해석 |
| --- | ---: | ---: | --- |
| 브랜드 상품을 가격순으로 첫 페이지 조회 | 99.897 | 1.868 | 인기 상품의 많은 관계를 세는 대신 저장된 개수를 읽어 빨라졌다. |
| 브랜드 상품을 가격순으로 중간 페이지 조회(앞의 25만 개를 건너뜀) | 137.207 | 140.614 | 해당 페이지의 좋아요는 적고 OFFSET 비용이 남아 개선이 없었다. |
| 전체 상품을 좋아요 많은 순으로 첫 페이지 조회 | 1606.975 | 769.974 | 반복 집계는 줄었지만 전체 후보의 결합·정렬은 남았다. |

첫 두 행은 페이지를 선택하는 쿼리 구조를 같게 맞췄다. 마지막 행은 기존 전체 좋아요순 구현과 비교했다. 상품·가격·좋아요 수·페이지 정보가 같은지도 확인했다.

## 6. Redis: 어떤 결과를 재사용할 것인가

카운터를 적용해도 같은 목록 요청마다 정렬·JOIN·전체 개수 계산을 반복한다. 브랜드·정렬·페이지·크기가 같은 목록 응답을 재사용하기 위해 Redis cache-aside를 선택했다. 캐시에 없으면 DB에서 읽어 저장하고, 있으면 저장한 결과를 사용한다.

| 대안 | 얻는 것 | 남는 비용 |
| --- | --- | --- |
| DB 조회만 유지 | 캐시와 원본의 불일치 관리가 필요 없음 | 같은 목록 계산을 반복 |
| 상품 ID별로 한 상품의 정보를 캐시 | 상품 하나의 이름·가격 등을 재사용하고 해당 상품 단위로 변경 처리 | 목록에 넣을 상품·순서·페이지·전체 개수는 별도로 계산 |
| **조회 조건별로 상품 목록 응답 전체를 캐시** | **상품들·반환 순서·전체 개수를 함께 재사용** | **상품 변경 시 여러 페이지의 캐시를 삭제해야 함** |

‘상품 10번의 이름·가격’을 저장하는 방식과 ‘브랜드 1의 가격순 첫 페이지 20개와 전체 개수’를 저장하는 방식의 차이다. 상품 하나의 캐시는 상세 조회와 목록 조립 모두에 사용할 수 있다.

대상은 `GET /api/v1/products`의 공통 응답이다. 사용자별 좋아요 여부와 주문 정보는 넣지 않는다. 같은 조회 조건이면 사용자와 무관하게 공유하지만 조건이 다르면 별도 캐시를 사용한다.

목록 선택의 근거는 앞서 측정한 SQL 비용이다. 실제 트래픽에서 같은 조건이 얼마나 반복되는지와 캐시 재사용률은 이후 확인한다.

## 7. 변경이 잦은 데이터는 어떻게 다뤘나

### 상품·브랜드 변경: DB 커밋 후 상품 목록 캐시 삭제

상품 생성·삭제·가격 변경은 목록의 순서와 여러 페이지를 바꿀 수 있다. 영향받는 페이지를 추적하는 대신, 상품 생성·이름/가격 수정·삭제와 브랜드 이름 변경·삭제 시 전체 상품 목록 캐시를 지우기로 했다. DB 커밋 후 삭제하고 롤백하면 유지한다.

이 방식은 삭제 대상을 관리하기 쉽지만 키가 많으면 삭제 작업과 후속 DB 조회가 늘어난다. 삭제 시도는 시간·횟수를 제한하고 미완료된 캐시는 TTL로 만료시킨다.

### 좋아요 변경: DB는 즉시, 목록 표시는 만료 후 반영

| 대안 | 장점 | 비용 |
| --- | --- | --- |
| 좋아요 변경마다 상품 목록 캐시 삭제 | 다음 조회에서 새 개수·순서를 계산 | 변경이 잦으면 재사용 전에 삭제될 수 있음 |
| **목록의 개수·순서를 TTL까지 유지** | **좋아요 변경마다 목록을 다시 계산하지 않음** | **만료 후 재조회까지 이전 개수·순서를 표시** |
| 상품 정보만 캐시하고 개수·순서는 DB에서 조회 | 조회 시점의 개수·정렬을 얻음 | hit에도 카운터 조회와 인기순 정렬이 남음 |

목록 표시용 좋아요 수·순서는 잠시 이전 값을 허용한다. **DB 관계·카운터는 즉시 변경하고, 목록 캐시만 만료 후 다음 요청에서 새로 만든다.**

### TTL: 25~30초, hit에서 연장하지 않음

캐시 저장 시 25~30초 사이의 만료 시간을 무작위로 정한다. 표시 지연을 짧게 두면서 목록을 재사용하기 위한 초기값이며, 측정으로 확정한 최적값은 아니다. 재사용률·DB 조회 감소·변경 반영 지연을 보고 조정한다.

무작위 TTL은 비슷한 시점에 저장한 여러 키의 만료를 분산한다. 같은 인기 키 하나에 몰리는 동시 miss는 합치지 못한다. 요청 합치기나 분산 락은 도입하지 않았다.

## 8. 실패할 때 무엇을 지키고, 무엇을 허용했나

| 상황 | 처리 |
| --- | --- |
| Redis에서 캐시를 읽지 못함 | 제한된 대기 후 DB에서 목록을 조회한다. |
| Redis에 결과를 저장하지 못함 | DB에서 읽은 결과로 응답한다. |
| DB 커밋 후 캐시 삭제 실패 | DB 변경을 유지하고 이전 표시 값은 만료 후 재조회로 회복한다. |
| 변경 전에 읽은 결과가 캐시 삭제 뒤 늦게 저장됨 | 이전 표시 값의 일시 노출을 허용한다. TTL은 늦게 저장한 시점부터 시작한다. |
| 삭제 상품·브랜드가 캐시에 남음 | DB에서 삭제 여부를 확인한 뒤 목록을 다시 읽는다. |
| DB 조회 자체가 실패 | 빈 목록으로 숨기지 않고 오류로 처리한다. |

삭제된 상품을 노출하지 않기 위해 캐시 hit 뒤 해당 페이지 상품·브랜드의 삭제 여부를 DB에서 한 번 확인한다. 삭제가 발견되면 페이지와 전체 개수를 다시 조회해 빈자리를 채운다. 따라서 hit에도 DB 조회가 한 번 남는다.

늦은 채움에서는 DB 변경 후 한참 뒤 저장된 캐시에도 새 TTL이 붙을 수 있다. 30초는 캐시 저장 후 만료 상한이며, DB 변경 후 반영 기한을 뜻하지 않는다.

표시 가격·좋아요 수 등의 일시 지연과 별개로, 주문 확정 시 가격·재고·포인트는 DB에서 검증한다.

## 9. Redis 적용 후 확인한 결과와 남은 비용

실제 MySQL·Redis 통합 테스트에서 상품 3개를 준비하고 첫 페이지 2개를 요청했다.

| 조회 상태 | 목록·전체 개수 SQL | 삭제 여부 확인 SQL | 응답 비교 |
| --- | ---: | ---: | --- |
| DB 조회만 사용 | 2회 | 0회 | 기준 응답 |
| cache miss | 2회 | 0회 | 기준과 같음 |
| cache hit | 0회 | 1회 | 기준과 같음 |

hit에서 목록·전체 개수 계산을 생략하고 삭제 여부만 확인했다. 이 표는 SQL 수 검증이며 Redis 적용 전후의 응답 시간 비교는 아니다.

상품·브랜드 변경 후 캐시 삭제, 롤백, 좋아요 표시 지연, TTL 만료, 삭제 실패와 늦은 채움, 실제 Redis 중단·복구를 테스트했다. 전체 310개 테스트와 Checkstyle·ArchUnit이 통과했다.

깊은 OFFSET, 전체 좋아요순 정렬, 인기 카운터 행의 쓰기 경합, 같은 인기 키의 동시 miss는 남는다. 이후 실험에서 각 비용을 측정해 커서 페이지네이션·정렬 인덱스·요청 합치기 등을 비교한다.

실험 환경 준비와 실행 명령은 [재현 안내](reproduce.md)에 정리했다.
